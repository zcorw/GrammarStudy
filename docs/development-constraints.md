# 开发约束文档

## 1. 目的

本文档用于约束当前“日语文法学习 PWA”项目的开发方式，统一架构边界、命名、接口、数据库、前端实现、提交流程与测试要求。

本文档结合以下两类信息整理：

- 参考项目 `AlignSpeak` 的工程纪律与文档风格
- 当前项目已确认的产品、架构、UI、API 与 Starter Package 决策

适用范围：

- `apps/web`
- `apps/api`
- `docs/`
- `docker-compose.yml`

## 2. 项目基线

- 产品方向：文法卡片检索、AI 辅助创建、练习点评
- 平台：移动端优先 `PWA`
- 前端：`Vite + React + TypeScript`
- 后端：`FastAPI + SQLAlchemy + Alembic`
- 数据库：`PostgreSQL`
- 单仓：`pnpm workspace`
- 部署与联调基线：`Docker Compose`

首版主闭环：

`推荐/搜索 -> 优先复用公共文法 -> 未命中时创建 -> AI 生成结构化卡片 -> 学习/练习 -> 入公共库沉淀`

## 3. 强制工程约束

以下约束默认必须遵守，不满足时不应合并：

- 分层架构
- 单向依赖
- 职责隔离
- 可测试优先
- 扩展优先
- 禁止万能工具类
- 禁止控制层写业务逻辑
- 禁止组件直接发请求
- 禁止隐式耦合
- 文档与实现同步

额外强制项：

- 新增或修改文件统一使用 `UTF-8` 无 BOM
- 开发、联调、容器化运行统一通过 `docker compose`
- 结构化业务逻辑必须有明确落点，不能散落在页面、路由或脚本中

## 4. 分层架构约定

### 4.1 后端分层

后端按以下层次组织：

- `presentation`：FastAPI 路由、参数解析、鉴权入口、协议转换
- `application`：用例编排、流程控制、事务边界
- `domain`：领域模型、领域规则、纯业务判断
- `infrastructure`：仓储实现、数据库、外部模型服务、缓存、鉴权组件

依赖方向必须是：

- `presentation -> application -> domain`
- `infrastructure -> application/domain`

禁止：

- 路由层写核心业务规则
- application 反向依赖 presentation
- domain 依赖 FastAPI、SQLAlchemy Session、HTTP 客户端
- 通过“公共 utils”跨层偷渡业务逻辑

### 4.2 前端分层

前端按以下边界实现：

- `view`：页面、组件、布局、交互容器
- `application/usecase`：页面动作编排、状态转换、流程控制
- `domain`：文法卡片、创建流程、练习规则等纯业务对象与规则
- `infrastructure`：HTTP API、浏览器存储、PWA 能力封装

依赖方向必须是：

- `view -> application -> domain`
- `infrastructure -> application/domain`

禁止：

- React 组件直接调用 HTTP
- 页面组件直接写检索排序、创建规则、权限判断
- 用全局隐式状态或初始化顺序隐式驱动核心流程

## 5. 当前领域术语（固定）

当前项目统一使用以下领域术语：

- `GrammarEntry`：公共库正式文法卡片
- `CreationSession`：创建流程中的临时会话
- `PracticeQuestion`：文法选择题
- `SentenceFeedback`：自由造句 AI 点评结果
- `UserProgress`：最近浏览、练习记录、收藏等用户学习数据

搜索结果固定术语：

- `best_match`
- `similar_cards`
- `search_confidence`
- `should_offer_ai_generation`

前后端、文档、测试、数据库命名必须优先复用这些术语，避免同义词混用。

## 6. 目录与模块约定

### 6.1 后端模块

后端首版模块固定为：

- `auth`
- `search`
- `grammar`
- `creation`
- `practice`
- `user`

新增功能优先归入以上领域；只有当出现新的稳定业务边界时，才新增一级模块。

### 6.2 前端页面

前端首版页面清单固定为：

1. 首页/发现页
2. 检索结果/推荐复用页
3. 文法详情/学习页
4. 选择题练习页
5. 创建流程页
6. 自由造句 AI 点评页
7. 登录页
8. 我的文法页

页面约束：

- 首页推荐优先，搜索始终可达
- 检索结果页与详情页应尽量复用文法卡片展示骨架
- 选择题练习必须独立页面，不嵌在详情页主体中
- 自由造句点评独立页面
- 创建流程必须是分步骤流程

## 7. 命名约定

- 代码标识符统一英文
- 文档内容默认中文
- 必要代码注释统一英文
- API 字段统一 `snake_case`
- TypeScript 类型、组件、类名使用 `PascalCase`
- 变量、函数、hook 使用 `camelCase`
- 布尔值命名使用谓词形式，如 `is_logged_in`、`has_invite_code`、`should_offer_ai_generation`

如果项目使用字符串主键，推荐前缀：

- `usr_`：用户
- `grm_`：文法卡片
- `ses_`：创建会话
- `prq_`：练习题
- `sfb_`：点评结果
- `fav_`：收藏记录
- `inv_`：邀请码

## 8. API 约定

### 8.1 基础约定

- 风格：`REST`
- 数据格式：`JSON`
- 路径前缀：`/api/v1`
- 时间格式：`ISO 8601`
- 鉴权方式：`JWT + 匿名 session`
- 受保护接口使用 `Bearer Token`

### 8.2 错误响应

错误响应统一为：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Human readable message",
    "details": {}
  }
}
```

约束：

- 不直接把底层异常文本暴露给客户端
- 错误码必须稳定
- 行为错误和系统错误要可区分

### 8.3 创建流程顺序

创建流程的 API 调用顺序固定为：

1. 先检索
2. 再决定是否创建
3. 创建后可追加提问
4. 最后确认入库

禁止：

- 跳过检索直接触发 AI 创建
- 在创建完成后继续通过 follow-up 修改公共卡片

## 9. 数据与数据库约定

### 9.1 基础约定

- 数据库使用 `PostgreSQL`
- 所有时间字段优先使用 `timestamptz`，统一按 UTC 处理
- 正式卡片与创建会话必须分离建模
- 标签优先结构化字段，少量自由标签作为补充
- 外键默认优先 `RESTRICT`，避免误删主数据

### 9.2 文法检索字段

正式文法卡片至少要预留以下检索相关字段：

- `title_raw`
- `title_normalized`
- `title_reading_kana`
- `aliases`
- `aliases_reading_kana`

约束：

- 用户输入汉字时，检索必须能走注音统一路径
- 搜索排序优先复用公共库，不直接默认走 AI 创建

### 9.3 首版业务规则

- 公共库允许重复或近重复项存在
- 创建前做软去重提示，但不做强阻断
- 创建流程中的版本历史只保存在客户端本地
- 自由造句点评结果不反向修改公共卡片
- 游客只能查看卡片和做选择题
- 登录用户才能创建文法、使用自由造句点评、同步个人数据

### 9.4 准入与账号

首版账号与准入规则：

- 注册与登录都使用邮箱 + 密码
- 首版不做邮箱验证码验证
- 注册时可选填写邀请码
- 无邀请码时进入管理员审核
- 登录只负责认证，邀请码与审核只影响账号是否通过准入
- 审核首版先允许通过数据库手工改状态完成

## 10. 前端实现约定

### 10.1 页面与组件

- 组件只负责展示与交互触发
- 页面容器只负责状态组织与 usecase 调用
- 业务判断进入 `domain` 或 `application`
- 接口调用统一进入 `infrastructure/api` 或 `repositories`

禁止：

- 在组件内直接 `fetch` / `axios`
- 在页面 JSX 中直接拼业务规则
- 通过大型 `utils.ts` 聚合多域逻辑

### 10.2 状态管理

- 状态就近管理
- 只有跨页面共享时，才上升到全局 store/context
- 异步交互必须有加载态、错误态和可重试路径
- 本地草稿和最近记录可放浏览器本地存储，但要有明确边界

### 10.3 UI 一致性

- `ui-static/` 当前以 `preview-site` 镜像版本为 UI 原型基线
- React 落地实现时必须保持页面职责与主要信息层级一致
- 详情页必须展示例句
- 练习页与详情页必须分离
- 检索结果页、详情页、创建流程页中同一张文法卡片的核心字段展示尽量一致

## 11. 后端实现约定

### 11.1 路由层

路由层只做：

- 参数解析
- Pydantic 校验
- 鉴权依赖挂载
- 调用 usecase/service
- 响应模型映射

禁止：

- 写检索排序规则
- 写创建/入库业务决策
- 写权限边界细节
- 写数据库查询拼装细节

### 11.2 服务与适配器

- AI 模型接入统一走适配器或 service 抽象
- 首版可以只接一个供应商，但不能把供应商细节散落在业务层
- 数据库访问通过 repository 或明确的数据访问层集中管理
- Pydantic 模型用于请求/响应契约，不直接替代领域对象

## 12. 第三方依赖策略

- 对通用能力优先使用成熟库，不重复造轮子
- 开发中的功能或组件如已有成熟、持续维护且许可证可接受的第三方包可用，应直接使用第三方包，不自行实现同类基础能力
- 典型能力包括：HTTP、日期处理、校验、密码哈希、JWT、数据库迁移
- 若选择自行实现，PR 必须说明：
  - 为什么现有库不适合
  - 维护成本和风险
  - 后续替换或长期维护计划

依赖选择基线：

- 持续维护
- 许可证可接受
- 体积与复杂度可控
- 无已知高危漏洞

## 13. 安全约定

- 禁止提交密钥、凭据、token
- 日志不记录密码、邀请码、完整敏感 payload、完整 token
- 用户隔离查询必须显式附带 `user_id` 或可追溯的用户归属条件
- 密码必须使用成熟哈希算法存储，禁止明文
- 邀请码、审批状态、账号状态必须是可追踪字段，不能只靠前端状态判断

## 14. 测试与质量约定

### 14.1 最低测试要求

后端重点覆盖：

- 检索逻辑
- 创建流程主链路
- AI 输出结构校验
- 入库规则
- 游客/登录用户权限边界

前端重点覆盖：

- 首页推荐与搜索主流程
- 检索结果与详情页跳转
- 详情页到练习页、点评页的跳转
- 创建流程关键步骤状态
- 登录、邀请码、审核状态分支

### 14.2 测试分层

- domain/usecase 优先单测
- API 做契约测试
- 至少保留一条端到端主链路

### 14.3 合并前检查

至少应完成：

- lint
- type-check
- relevant tests
- 文档同步

## 15. 提交与评审约定

### 15.1 提交原则

- 单个 PR 只做一类变更
- 优先最小可验证改动
- 用户可见行为变更必须附验证方式
- 涉及架构、接口、数据边界的修改必须同步更新文档

### 15.2 分支建议

- `feat/<topic>`
- `fix/<topic>`
- `docs/<topic>`
- `refactor/<topic>`
- `test/<topic>`

### 15.3 提交信息

遵循 Conventional Commits：

- `feat: ...`
- `fix: ...`
- `docs: ...`
- `refactor: ...`
- `test: ...`
- `chore: ...`

### 15.4 PR 最低清单

- 背景与目标
- 实现方案
- 影响范围
- API / 数据结构变更
- 测试结果或人工验证步骤
- 文档同步说明

### 15.5 评审重点

- 正确性
- 架构一致性
- 可维护性
- 安全性
- 可测试性
- 可观测性

## 16. Docker Compose 约定

开发、联调、容器化验证统一使用 `docker compose`。

常用命令：

- `docker compose up -d --build`
- `docker compose down`
- `docker compose logs -f <service>`
- `docker compose up -d --build <service>`

如果工作目录包含非 ASCII 路径，Windows Docker 构建上下文可能出现兼容性问题；需要使用 ASCII 路径快照或等效方案执行构建。

## 17. 文档同步约定

以下变更必须同步更新相关文档：

- 页面结构变化：更新 Stage 4 / UI 约束文档
- 模块边界变化：更新 `docs/architecture.md`
- API 字段或错误结构变化：更新 `docs/api-overview.md`
- Starter Package 结构变化：更新 `docs/stage-09-final-starter-package.md` 或 README

文档要求：

- 可执行
- 可验证
- 尽量给出真实示例
- 避免空泛描述
